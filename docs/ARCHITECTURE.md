# Архитектура модуля клиентов и обращений

Модуль `backend/crm/sales` отделяет бизнес-операции от HTTP и представления данных. Для хранения применяется Django ORM. Отдельный универсальный Repository поверх ORM не вводится: он повторял бы уже существующий интерфейс без самостоятельной задачи.

## Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| `crm/models.py` | Хранение данных, связи, ограничения и индексы |
| `sales/validation.py` | Преобразование и проверка входных полей |
| `sales/selectors.py` | Доступные сотруднику клиенты и обращения, поиск записи в области доступа, пагинация |
| `sales/services.py` | Создание и изменение карточек, назначение ответственных, смена этапов, комментарии и транзакции |
| `sales/serializers.py` | Преобразование моделей в данные ответа |
| `sales/views.py` | Разбор запроса и вызов операций, формирование HTTP-ответа |
| `crm/http.py` | Общая проверка метода, сессии, JSON и обработка ошибок API |

Важные правила проверяются внутри сервисов, а не только во views. Это позволяет повторно использовать операции из команд и будущих интеграций. Чтение проходит через selectors. Направление зависимостей: HTTP → сервисы/выборки → модели. Сервисы не импортируют HTTP-обработчики и не возвращают JsonResponse.

## Доступ и целостность

Каждый клиент и обращение принадлежат организации. Родственник принадлежит карточке клиента и наследует её границу доступа. Телефон не является уникальным идентификатором человека; одинаковые номера не объединяют клиентов автоматически.

Владелец, администратор и руководитель работают с обращениями компании. Менеджер видит свои назначенные обращения и связанные с ними карточки, а также созданные им карточки без обращений. При общей карточке клиента история чужих обращений менеджеру не возвращается. После переназначения единственного обращения бывший ответственный теряет доступ к нему и карточке, если других оснований доступа нет.

Создание обращения проверяет клиента, активного ответственного и филиал в одной компании. Менеджер может назначать обращение только себе. Проверки выполняются сервером независимо от доступных в интерфейсе вариантов.

Для изменений клиентских карточек и обращений применяется Optimistic Locking: клиент отправляет прочитанную `version`, сервер блокирует запись на время изменения и отвергает устаревшую версию с кодом 409. Назначение сотрудников дополнительно сериализуется блокировкой компании вместе с отключением доступа. При росте нагрузки ширину этой блокировки можно уменьшить после измерений.

Создание обращения и запись истории выполняются в одной транзакции. Отказ требует причины. Произвольный запрет возвращаться на предыдущие этапы не введён: бизнес-правило для этого пока не определено. Этапы представлены enum; отдельный State pattern имеет смысл при появлении различающихся правил перехода, а не для простого списка значений.

## Интерфейс

`web/src/components/sales.tsx` координирует список клиентов и доску обращений. Редакторы клиента и обращения вынесены в `sales/client-editor.tsx` и `sales/lead-editor.tsx`. Общие поля, диалог, типы данных и состояние выполнения операций переиспользуются через композицию и небольшой hook. Общий кабинет отвечает за выбор компании и навигацию.

Поиск выполняется на сервере с задержкой ввода. Списки загружаются страницами по 50 записей. Счётчики этапов относятся ко всем доступным результатам текущего фильтра, карточки на доске — к загруженным страницам; кнопка «Загрузить ещё» подгружает следующие. Клиент не выбирается автоматически по совпавшему имени или номеру.

## Границы реализации

Работают создание и редактирование клиента, добавление контактных лиц, обращения, поиск, фильтр этапов, назначение ответственного, следующий контакт и история с комментариями. Следующий контакт — дата в обращении. Наступившие даты отображаются в напоминаниях внутри открытой CRM. Контакты родственников пока можно добавлять, но нельзя редактировать или удалять. Добавлен отдельный список задач с выполнением, переносом срока и возвратом в работу. Экспорт, архивирование и передача в RehubPro остаются следующими этапами.

Статус «Поступил» фиксирует факт в CRM и не создаёт резидента в другой системе. Полного разделения Person/ContactRelationship для повторного использования одного родственника в нескольких карточках пока нет: контактные лица хранятся внутри карточки, без неявного объединения людей.

## Стиль и проверки

Python форматируется Ruff, TypeScript и CSS — Prettier. Зависимости инструментов фиксируются в `backend/requirements-dev.txt` и `web/package-lock.json`. Для установки Python-инструментов используйте `.venv/bin/python -m pip install -r backend/requirements-dev.txt`.

Проверки: `.venv/bin/ruff check backend`, `.venv/bin/ruff format --check backend`, из `web` — `npm run format:check` и `npm run build`. Бизнес-правила, доступ и устаревшие версии покрыты тестами; параллельные операции проверяются на PostgreSQL.

## Задачи и сводка

`backend/crm/work` содержит отдельные selectors, services, serializers и views. FollowUpTask принадлежит обращению и наследует его компанию и ответственного; второго независимого назначения нет. При переназначении обращения связанные задачи переходят новому ответственному. Все выборки проходят через правила видимости обращений.

Изменение задачи использует транзакцию, блокировку записи и проверку версии. История задачи записывается в историю обращения атомарно. Сводка считает только доступные сотруднику данные. Завершённые и отказанные обращения не создают напоминания о следующем контакте; открытые задачи продолжают отображаться до их явного выполнения.

Напоминания вычисляются из сроков на сервере, без создания дублирующихся уведомлений при каждом чтении. Интерфейс обновляет их раз в минуту, пока открыта соответствующая панель. Это не фоновая доставка: для email, push и работы при закрытом кабинете понадобится отдельный механизм. Автообновление задач приостанавливается при редактировании формы, чтобы не заменять несохранённые значения.

Оформление RehubPro централизовано в `web/src/app/rehub-theme.css`; основные цвета не дублируются в токенах базового CSS.

## Интеграция центров

`crm/integrations` разделён на address, secrets, selectors, services, transport, delivery и views. Service Layer определяет бизнес-операции, Transactional Outbox сохраняет доставку в одной БД, HTTPSClient является Adapter. Узкий Transport Protocol позволяет подменить сеть в тестах без подмены бизнес-логики и модели Resident. Повторяемость операций обеспечивают Idempotent Receiver на RehubPro и неизменяемый снимок в CRM. Fencing token аренды защищает результат от опоздавшего исполнителя.

`rehubpro-main/crm_bridge` следует структуре существующего проекта: models, services, views, migrations и management commands. Приёмник по умолчанию выключен. Существующая модель Resident не менялась; новые данные контактов доступны в записи приёма. Операционные шаги и ограничения описаны в INTEGRATION.md.
