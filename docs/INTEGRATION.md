# Передача клиента из CRM в RehubPro

Реализованы настройки центров компании, подтверждение поступления, сохранение неизменяемого снимка, доставка из очереди БД и приёмный модуль `rehubpro-main/crm_bridge`. Проверки выполняются локально; действующие серверы не обновлялись.

## Адрес центра

В настройках компании владелец или администратор вводит название и адрес. Например, `test.rehubpro.kz/qqweqw/qweqwe` превращается в домен `test.rehubpro.kz`. Схема всегда HTTPS; путь, параметры и фрагмент исходной ссылки отбрасываются. API строится фиксированно:

| Метод | Адрес | Назначение |
| --- | --- | --- |
| GET | `https://test.rehubpro.kz/crm/health` | Проверка ключа и привязки к компании и подключению |
| POST | `https://test.rehubpro.kz/crm/create` | Подтверждённое поступление |
| GET | `https://test.rehubpro.kz/crm/admissions/{operation_id}` | Проверка результата в рамках этого подключения |

Логины в URL, IP-адреса, HTTP и нестандартные порты не принимаются. По умолчанию запросы разрешены только к `rehubpro.kz` и его поддоменам. Другие публичные домены администратор платформы добавляет в `CRM_CENTER_ALLOWED_DOMAINS`, разделяя запятыми. Это настройка доверия, недоступная пользователю компании.

HTTPS-адаптер проверяет все адреса DNS и отклоняет ответ с внутренним адресом. Подключение фиксируется к проверенному публичному IP с проверкой TLS-сертификата исходного домена. Прокси окружения не используются. Редиректы не выполняются: ключ нельзя передать на адрес перенаправления.

## Подключение центра

1. В CRM добавьте название и адрес центра. В карточке появятся идентификаторы компании и подключения и готовая команда выдачи ключа.
2. На тестовом RehubPro установите исходники `crm_bridge` и изменения `config/settings.py`, `config/urls.py`, `licenses/middleware/license_check.py`. Приложение добавляет только новые таблицы; существующая модель Resident не изменяется.
3. Обычной командой центра выполните `python manage.py migrate`. Выдайте ключ командой из карточки CRM:

```bash
python manage.py issue_crm_key --company COMPANY_UUID --connection CENTER_UUID
```

4. Скопируйте выданный ключ в карточку центра CRM и сохраните. Открытый ключ отображается при выдаче один раз. На RehubPro хранится только SHA-256, в CRM — шифротекст Fernet.
5. В окружении этого RehubPro установите `CRM_BRIDGE_ENABLED=1` и перезапустите приложение. Без этого приёмник отвечает 503. HTTPS, лицензия центра и его сетевые правила должны разрешать запросы от сервера CRM.
6. В CRM нажмите «Проверить подключение». Ответ должен подтвердить именно эту компанию и это подключение. Только проверенный активный центр доступен для передачи.

Ключ действует 90 дней. Та же команда заменяет ключ, сохраняя историю и защиту от дублей. После замены сохраните новый ключ в CRM и повторите проверку. Для отзыва:

```bash
python manage.py issue_crm_key --company COMPANY_UUID --connection CENTER_UUID --revoke
```

В Django admin RehubPro можно отключить CrmCredential. Удаление записей приёма через admin запрещено, чтобы не потерять защиту от повторов. IP/device-политика центра не обходится. Для истёкшей лицензии `/crm/` возвращает JSON 403 вместо браузерного redirect.

## Шифрование в CRM

Перед сохранением ключей требуется `CRM_INTEGRATION_KEY` — постоянный Fernet-ключ, отдельный от БД. Новый `scripts/setup.sh` генерирует его для нового `.env`. При обновлении ранее созданной установки добавьте ключ вручную, например сгенерировав его в своём терминале:

```bash
.venv/bin/python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Сохраните результат в `CRM_INTEGRATION_KEY` и перезапустите процессы CRM. Нельзя заменять этот ключ без процедуры расшифрования/перешифрования сохранённых подключений. Храните его в резервной копии конфигурации отдельно от резервной копии базы. API никогда не возвращает сохранённый ключ.

## Подтверждение и состав данных

В карточке обращения владелец, администратор или руководитель выбирает центр, указывает отдельно фамилию, имя, отчество и фактическую дату поступления. Автоматическое разбиение ФИО на части не выполняется. Перед подтверждением видны дата рождения, телефон, город и до двадцати контактных лиц. Заметки клиента, комментарии и история общения не отправляются.

CRM проверяет версии карточки клиента и обращения: данные не должны измениться после предпросмотра. Подтверждённая передача хранит снимок данных. Изменение карточки после постановки в очередь не меняет уже подтверждённое поступление.

Контракт версии 1:

```json
{
  "schema_version": 1,
  "external_admission_id": "4ddf405f-1b4b-40f3-8878-dad318c821ac",
  "external_client_id": "99c3b171-5618-4b7c-a63a-e3ddf341eeed",
  "person": {
    "last_name": "Тестовый",
    "first_name": "Клиент",
    "middle_name": "",
    "date_of_birth": null
  },
  "admission": {"date_of_admission": "2026-11-13"},
  "contact": {"phone": "", "city": ""},
  "relatives": []
}
```

Заголовки: `Authorization: Bearer KEY`, `Content-Type: application/json`, `Idempotency-Key: EXTERNAL_ADMISSION_UUID`. Пример синтетический. Приёмник получает организацию из ключа, а не из переданных пользователем полей.

На RehubPro создаётся Resident с именем, датой рождения и датой поступления. Телефон, город и родственники сохраняются в AdmissionReceipt вместе со снимком и доступны уполномоченному администратору RehubPro. Они пока не переносятся автоматически в СОЗА: текущая модель телефонов при сохранении обращается во внешний WhatsApp gateway. Интеграция не должна неявно запускать эту регистрацию номера.

Ответ при создании — 201, при идентичном повторе — 200:

```json
{
  "schema_version": 1,
  "external_admission_id": "4ddf405f-1b4b-40f3-8878-dad318c821ac",
  "resident_id": 42,
  "status": "delivered"
}
```

Факт доставки не меняет этап обращения автоматически. Менеджер отдельно фиксирует этап «Поступил»; сеть и бизнес-событие не отождествляются.

## Защита от дублей

В CRM уникальна пара обращения и центра. Повторное подтверждение идентичных данных возвращает ту же операцию; другой снимок для этой пары даёт 409. Домен центра с существующими передачами менять нельзя; для другого центра создаётся новое подключение.

На RehubPro сохранение Resident и AdmissionReceipt выполняется одной транзакцией. Уникальны пары компании с external_admission_id и компании с external_client_id. Одинаковая операция и одинаковое тело возвращают прежнего резидента; изменённое тело или новый номер операции для уже переданного клиента дают 409. Защита сохраняется при замене ключа и при использовании разных подключений той же компании к одному инстансу.

Это защита повторов CRM, а не автоматическое установление личности по имени или телефону. Ранее созданного вручную резидента и повторное поступление необходимо разобрать в центре. Автоматическое объединение людей не выполняется.

## Очередь и доставка

AdmissionTransfer одновременно является бизнес-записью и записью Transactional Outbox. Потери задания между commit и публикацией в отдельный broker нет: исполнитель подбирает очередь непосредственно из БД. Для этой функции Redis/Celery не требуются.

Из `backend`:

```bash
../.venv/bin/python manage.py run_worker
```

Один проход (передача, сообщение очереди и напоминания):

```bash
../.venv/bin/python manage.py run_worker --once
```

В локальном `scripts/dev.sh` исполнитель стартует вместе с API и интерфейсом. В рабочем окружении запускайте отдельным сервисом с автоматическим перезапуском. Для нескольких исполнителей нужна PostgreSQL: захват использует `SELECT FOR UPDATE SKIP LOCKED`. SQLite остаётся только удобным локальным режимом; не используйте его для нескольких исполнителей.

Задание получает аренду на 120 секунд и уникальный lease_id. После остановки процесса просроченная аренда подбирается снова. Завершение старым исполнителем не может перезаписать результат нового. История попыток остаётся в БД; у оборванной попытки результат может быть неизвестен.

| Ситуация | Поведение |
| --- | --- |
| Сеть, таймаут, HTTP 429 или 5xx | До восьми попыток с увеличением интервала, случайной задержкой и учётом Retry-After |
| 200/201 с совпавшей операцией и resident_id | Подтверждённая доставка |
| Неверный успешный ответ | Повтор той же операции с ограничением попыток |
| HTTP 401/403 | Пауза; проверить ключ, лицензию и сетевой доступ |
| HTTP 409 | Конфликт; ручная проверка центра |
| Другие 4xx | Ошибка данных/адреса без автоматических повторов |
| Redirect | Остановка без следования перенаправлению |
| Центр отключён или непроверен | Пауза без отправки |

Ручной повтор после устранения проблемы использует тот же идентификатор и тот же снимок. История попыток не сбрасывается; начинается новый цикл до восьми автоматических попыток. Сырые ответы центра, ключи и содержимое карточки не записываются в журналы ошибок доставки.

## Проверки

Временная БД PostgreSQL проверяет конкурирующих исполнителей, идемпотентный приём и повтор после потерянного ответа. Сквозной тест использует настоящий Resident и HTTP-обработчик приёмника, с подменой только сетевого транспорта.

Для сквозного набора локально установите `backend/requirements-bridge-tests.txt`, затем из `backend`:

```bash
CRM_DB_ENGINE=postgres ../.venv/bin/python manage.py test crm.tests crm_bridge.tests --settings=crm.tests.bridge_settings --noinput
```

Эти тестовые настройки подключают соседний исходный проект только для тестов. Рабочая CRM от его Python-модулей не зависит. Действующий сервер и внешние домены в тестах не используются.
