# Существующий RehubPro и точки интеграции

Разбор локального проекта `../../rehubpro-main` на 13 ноября 2026 года. Выводы относятся к этой копии, а не к проверенному состоянию продакшена.

## Архитектура локального проекта

| Наблюдение | Основание | Значение для CRM |
| --- | --- | --- |
| Backend построен на Django, данные хранятся в PostgreSQL | `config/settings.py`, `requirements.txt` | Адаптер приёма можно добавить отдельным Django-приложением |
| Есть отдельный Next.js интерфейс | `rct/package.json` | Стек знаком проекту; код интерфейса CRM следует развивать отдельно |
| Инстанс использует настройки БД, `CLIENT_CODE` и Redis из окружения | `config/settings.py` | Подключать конкретное развёртывание, не считать `CLIENT_CODE` организацией общей CRM |
| Пример запуска включает web, next, celery и celery-beat в сети `core_backend` | `docker-compose.example.yml` | Повторение такого набора для каждой CRM-компании можно избежать общим сервисом |
| Пользователь имеет одно поле роли; связи с компанией нет | `users/models/user.py`, `users/models/enums.py` | Для общей CRM нужны Organization и Membership с ролью в компании |
| У Resident нет поля организации | `residents/models/resident.py` | Нельзя просто поселить компании в существующую общую базу и считать их изолированными |
| Создание резидента требует даты поступления, имени и фамилии | `residents/models/resident.py`, `residents/forms.py` | Заявка CRM и резидент различаются; передавать после подтверждения поступления |
| Нынешнее добавление использует форму и вход пользователя | `residents/views/add.py` | Для межсервисной передачи нужен отдельный API с ключом |
| Текущий ZIP-импорт переносит также медиа, метрики, психолога, отчёты и СОЗА | `residents/services/resident_import_service.py` | Он предназначен для переноса дела; его нельзя использовать как минимальный контракт передачи лида |
| ZIP-импорт сопоставляет Resident по identical_number | тот же сервис | Для CRM нужны отдельные внешние UUID и запись приёма; не подменять внутренний номер резидента |
| Телефоны связаны с профилем СОЗА и моделью contacts.PhoneNumber | `soza/models/soza_profile.py` | Отдельно спроектировать сопоставление контактных лиц и телефонов |
| Истёкшая лицензия вызывает redirect для большинства путей | `licenses/middleware/license_check.py` | Машинный endpoint должен давать определённый JSON-ответ, сохраняя лицензионные ограничения |

В локальном `config/urls.py` namespace лицензий уже `licenses`. Предупреждение о namespace `reminders` в существующем AGENTS.md не соответствует прочитанному файлу; запуск проверки Django в рамках этого разбора не выполнялся.

## Что сохраняем при разделении продуктов

RehubPro остаётся источником данных резидента после поступления: программа, отчёты, психологические сессии, СОЗА и учёт центра. CRM владеет обращением, коммуникациями менеджеров и подготовкой поступления. После передачи сохраняются внешние идентификаторы и состояние доставки, без автоматической двусторонней записи одних и тех же полей.

Базы, сессии пользователей и пароли двух продуктов не объединяются. Общий вход можно спроектировать позднее. Отдельный проект CRM допускает единый бренд, общий кабинет и пакетный тариф без копирования всей системы реабилитации.

Имена сети и сервисов в локальном compose — ориентир, не доказательство фактической схемы core.

## Объём текущих изменений

Первоначально создан соседний каталог `rehubpro-crm` с документацией. Затем в нём реализован первый этап CRM: отдельный Django API, Next.js интерфейс, компании, сотрудники и приглашения. Текущий статус и запуск описаны в README проекта.

Существующий `rehubpro-main`, его локальные изменения, база и развёртывания не изменялись. Копирование `.env`, лицензии, медиа и реальных клиентских данных в новый проект не выполнялось.
