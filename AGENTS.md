# RehubPro CRM

Это отдельный проект CRM. Не менять соседний `rehubpro-main` для реализации функций CRM без необходимости и явного включения интеграции в задачу.

## Структура

- `backend/config` — Django settings, URL и WSGI.
- `backend/crm/models.py` — аккаунты, компании, членства, филиалы, приглашения и аудит.
- `backend/crm/services.py` — бизнес-операции и проверки доступа.
- `backend/crm/views.py` — JSON API с сессиями и CSRF.
- `web/src` — Next.js App Router и TypeScript.
- `docs/PLAN.md` — последовательность работ и модель предметной области.

## Правила

Все пользовательские тексты на русском. Данные компаний не смешивать: каждый endpoint компании проверяет активное членство; связанные записи искать с фильтром компании, включая обновление и отзыв доступа. Глобальная роль пользователя не заменяет роль Membership.

Пароли, `.env`, содержимое писем с действующими ссылками, cookie и ключи не коммитить. Приглашения и подтверждения хранить хешированными. Не отключать CSRF ради работы интерфейса. Не доверять `organization_id` из тела запроса как доказательству доступа.

Для операций над приглашениями сохранять транзакции, блокировки и аудит. Изменения этой логики проверять на PostgreSQL, включая конкурентные тесты. Не писать реальные клиентские или медицинские данные в демо и тесты.

## Проверки

Из `backend`: `../.venv/bin/python manage.py check`, `../.venv/bin/python manage.py makemigrations --check --dry-run`, `../.venv/bin/python manage.py test crm.tests`.

Из `web`: `npm run typecheck` и `npm run build`. Сохранять зафиксированные зависимости и lock-файлы. Прочитать применимые инструкции `web/AGENTS.md` и документацию установленного Next.js перед изменением поведения framework.

PostgreSQL CRM запускается отдельным `docker compose up -d db`; её тесты создают и удаляют только `test_rehubpro_crm`. Не использовать БД RehubPro и не запускать команды удаления volumes для очистки тестов.

## Принципы разработки

Соблюдать SOLID, DRY и KISS. Бизнес-операции нового модуля размещать в `crm/sales/services.py`, правила видимости — в selectors, преобразования ответа — в serializers. Не дублировать проверки доступа в каждом экране и не переносить их только в интерфейс. Применять паттерны при наличии задачи, а не создавать универсальные фабрики, репозитории и интерфейсы без конкретной необходимости. Подробности в `docs/ARCHITECTURE.md`.

Форматирование и статические проверки: Ruff для Python, Prettier для TypeScript и CSS. Новые редакторы делать небольшими компонентами с явными типами входных данных.

## Доставка клиентов

Для интеграций использовать `crm/integrations`: services не зависят от HTTP, транспорт реализует узкий Protocol, очередь хранится в БД. Не менять снимок уже подтверждённой передачи и её идентификатор при повторе. Не ослаблять SSRF/TLS-проверки ради локального теста: для тестов подменять Transport. Ключи шифруются Fernet, не возвращаются API и не попадают в логи. Нельзя удалять историю приёмов в RehubPro: она обеспечивает идемпотентность.
